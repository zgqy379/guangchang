## 1. 风格定位声明

### 1.1 两层关系：UI 玻璃是**容器**，3D 孪生体是**内容**

```
┌──────────────────────────────────────────────────────────┐
│  UI 玻璃层（DOM，backdrop-filter）                        │  ← 容器：承载可读的信息
│   ┌────────────────────────────────────────────────┐     │
│   │  3D 孪生体层（WebGL，同一场景的光学校准）        │     │  ← 内容：参数本身的空间语言
│   │   · 玻璃体块 = 一个公司的空间                    │     │
│   │   · 数据体   = 一个参数的可感知物理量            │     │
│   │   · 实体小人 = 唯一的人类参照物                  │     │
│   └────────────────────────────────────────────────┘     │
└──────────────────────────────────────────────────────────┘
```

判定规则（唯一）：

> **凡是"信息"，就必须在 3D 里以物理量存在；凡是"信息的外壳/导航/数值读数"，就必须在 UI 玻璃里存在。**
> 二者不是两套设计，是**同一件东西的两面**——玻璃体是"参数的体积"，UI 玻璃是"读这个体积的仪器"。

这条规则直接解决了两个常见错误：

1. **UI 玻璃里再画一遍 3D 已经表达过的图形** → 重复。例：街区里已有钞票山，名片卡里就只放 `num` 26px 的总包数字，**不再放一个小山图标**。
2. **3D 里做需要精确阅读的东西** → 不可读。例：缴费基数 0.6 必须是 3D 里的**切口牌形状** + UI 里的**26px 数字**，二者是"形状 + 精确值"的关系，不是"两次显示同一个值"。

### 1.2 为什么要共用一套光学校准（OCC）

如果 UI 玻璃和 3D 孪生体各画各的，会出现"贴片感"——玻璃浮层像一张贴在屏幕上的 PNG，而不是空间里的一层介质。解法是让两者**遵守同一套光学规则**（Optical Calibration Contract, OCC）：

| 编号 | 规则 | UI 侧落地 | 3D 侧落地 |
|---|---|---|---|
| **OCC-1** | 主光方位统一：世界坐标方位角 **135°**、仰角 **55°**（光源恒定在"左上后"） | 玻璃顶部 1px 内高光（`inset 0 1px 0 0`）的最亮点落在元素**左上 8%** 处 | 孪生体玻璃上表面的反射带同样落在左上 8%–30%；`roughness .18`（日）使高光带**宽度 0.06–0.10m** |
| **OCC-2** | 模糊半径 ↔ 景深：`blur(28px)` 对应"焦点后方约 0.6m 视差深度的等效散焦" | 玻璃背板内容与玻璃平面**深度差 ≥0.6m** 时用 28px；≤0.6m 升到 36px；≥1.2m 降到 20px | 场景雾 near/far 与之联动（twin §3.1：日 `near 40 / far 190`） |
| **OCC-3** | 边缘描边同源：同一物件在 UI 与 3D 中的描边色必须来自同一令牌 | `--ui-glass-border`（日 `rgba(255,255,255,.18)` / 夜 `rgba(255,255,255,.55)`） | `theme.light.wire` @0.5（日）/ `theme.dark.wire` @0.8（夜） |
| **OCC-4** | 接触阴影同向：投影恒在"下方 + 后方"（光在左上） | `0 12px 32px -10px rgba(11,14,26,.45)` | 物体底部径向接触阴影贴图（复用现有 `shadowTexture()`） |
| **OCC-5** | 玻璃永远与场景"反明度" | 见 §1.3 反相表 | 孪生体玻璃永远与场景天幕"反明度"（日=冷白玻璃/深靛天；夜=深靛玻璃/星空） |

### 1.3 浅色 / 深色两套主题下这套关系如何成立

沿用 twin-style-spec v4 §2 矛盾 A 的反相规则，并把"反相"从"UI 玻璃"扩展到**整条光学校准链**：

| 项 | 浅色主题（08:30–17:30） | 深色主题（19:00–06:00） |
|---|---|---|
| 场景天幕 | `theme.light.skyTop → skyHorizon`（冷白） | `theme.dark.skyTop → skyHorizon`（深靛） |
| **UI 玻璃（容器）** | **深玻璃** `--ui-glass-fill` = `rgba(11,14,26,.72)` | **亮玻璃** `--ui-glass-fill` = `rgba(255,255,255,.72)` |
| UI 文字 | 白 `#FFFFFF` | 墨 `--color-neutral-0` `#0B0E1A` |
| **3D 孪生体（内容）** | 冷白玻璃 `theme.light.glassBody`，`opacity .62` | 深靛玻璃 `theme.dark.glassBody`，`opacity .55` |
| 3D 数据体 | 角色/行业色，`emissive 1.2` | 同色，`emissive 1.9` |
| 3D 描边 | `theme.light.wire` @0.5 | `theme.dark.wire` @0.8 |
| **关系** | **深容器装浅内容**（容器沉下去，内容浮上来） | **浅容器装深内容**（容器亮起来，内容沉下去） |
| OCC-2 模糊 | 浅背景 → `blur(28px)` + `saturate(180%)` | 深背景 → `blur(28px)`，`saturate(140%)`（避免夜光过饱和） |
| OCC-3 描边 | `rgba(255,255,255,.18)`（深玻璃上需亮描边才可见） | `rgba(255,255,255,.55)` |

> **一句话**：玻璃 UI 是"与场景相反明度的那一层"。浅色场景里它是深色浮层，深色场景里它是亮色舷窗——两者都自动从背景里"浮"出来，容器/内容关系不需要额外处理。

### 1.4 首屏（角色选择）的特殊光学处理：预览龛

首屏背景是 3D，但**不能直接把 UI 玻璃压在 3D 上**——浅色主题下卡片会变成两块突兀的深色矩形，深色主题下则糊进夜景。解法：

- 每个角色卡内部开一个 **「预览龛」（preview niche）**：卡片内嵌的 208px 高视窗，四角内收 8px，圆角 16。
- 龛内是一个**独立的微型孪生场景**（**纯 SVG / CSS，不建 WebGL 上下文**），自带**暗色影棚背景**（CSS 背景层，从 `#0B0E1A` 渐变到 `#1a2740`，配 `--theme-* wire` 1px 网格 @0.18），**因此在浅/深两个主题下都读得出**（发光强调色对影棚背景对比 6.57:1 / 5.59:1）。
- CSS 侧只叠一层**径向暗角**（`--role-niche-vignette`，`rgba(11,14,26,.42)`，中心透明 → 边缘压暗）做取景框收束，**不做平涂遮罩**——平涂会把发光粒子压死。
- 结果：卡片本体是"容器"，龛是"容器里的另一个世界"——**双层嵌套，恰好演示了 §1.1 的容器/内容关系**。

### 2.2 零资产预览龛（首屏**不加载任何 3D 资产**）

> **主理人硬约束（2026-10-27 追加）**：HR 形象池 9 个 GLB 共 **16MB**、办公空间 4 套 SPZ 共 **17MB**、玩家 Avatar **3MB**。首屏 5MB 红线 ⇒ **角色选择首屏必须零 3D 资产加载**，只能靠 CSS/SVG 剪影表达角色差异，3D 资产等选完角色后再懒加载。

#### 2.2.1 结论：首屏**不创建 WebGL 上下文**

| 方案 | 首屏增量 | 结论 |
|---|---|---|
| 跑完整招聘街区（64 摊位 + 门楣 LED + 门面） | ≥20MB 资产 + 64 lot 构建，TTI 远超 3s | ❌ 否决 |
| 跑「双龛 3D rig」（Phase 1 原提案，需 1 个 GLB + three.js） | three.js + R3F ≈ 600KB gzip + 1 个 GLB ≈ 1.8MB + draw call 成本 | ❌ **已撤回**（见 §2.2.5，主理人 2026-10-27 追认） |
| **纯 DOM + CSS + 内联 SVG 剪影（本方案）** | **3D 资源 0 bytes**、JS 增量 ≤ 60KB gzip、HTML+CSS+SVG < 40KB | ✅ **采用（唯一方案）** |

**两条硬红线（可机检，写进 §9.1 验收）**：

```js
// 红线 1：首屏不得存在任何 WebGL 上下文
document.querySelectorAll('canvas').forEach(c => {
  // 期望：c.getContext('webgl2') === null && c.getContext('webgl') === null
});
// 红线 2：首屏网络请求中不得出现 .glb / .spz / .ktx2 / .ply
// 期望：DevTools Network 面板按类型过滤后为 0 条
```

> **为什么把「0 个 WebGL 上下文」也列为红线**，而不只是「0 字节资产」：
> 1. iOS Safari 的 WebGL 上下文有**真实的内存上限**，多一个上下文就多一份"打开即崩"的风险面；
> 2. 主理人已追认本方案：**首屏最大的风险是"打开即崩"，不是"不够炫"**；
> 3. 选完角色 2 秒后就进真 3D 街区，第一印象本来就建立了——首屏的"炫"是冗余的。
> **首屏不是 3D 的门面，是 3D 的门牌**：它要的是 0.3 秒打开、0 崩溃，而不是 30fps。

**结论的三个理由**：
1. **体积**：0 资产是唯一能同时满足「5MB 首屏」和「首屏可交互 ≤3s」的方案。
2. **性能**：CSS 动画走 transform/opacity 合成层，不触发 layout/paint → 60fps 无 WebGL 开销。
3. **可交付**：SVG 是矢量的，"降级成静态图"这一步根本不需要——**最坏情况就是 SVG 静止**，没有资产管线、没有预渲染步骤。

> **首屏不再有 3D 的代价与补偿**：第一印象里没有"真的 3D 在动"。补偿手段是 **① 玻璃质感的 SVG 剪影**（渐变 + 内高光 + 模糊投影 + 描边，做到"看起来像 3D 截图"）、**② 明确的文案预告**（「进入后是 3D 街区 · 64 个招聘摊位」）、**③ 选完角色后立刻进入真实 3D**。这条代价已登记为 **R13**。

#### 2.2.2 预览龛的结构（纯 SVG）

```
┌──────────────────────────┐  龛：208px 高（桌面）/ 184（平板）/ 168（手机）

│ │  │ 24 粒子      │ │ 参数碑缩影 ││
│ │  │ 3 片作品卡   │ │ 头顶日月   ││
```

**两龛共用一套光学参数**（保证"同一世界"暗示）：
- 同一条人形剪影 path（高 120px ↔ 1.60m），同一渐变填充（`--role-niche-backdrop-top → --role-niche-backdrop-bottom`），同一描边（`--theme-* wire` @0.35，1px）
- 同一暗角层、同一阴影（`0 8px 18px -6px rgba(11,14,26,.32)`）
- 同一动画曲线（`cubic-bezier(.22,1,.36,1)`）与同一周期（3.2s）
- **唯一的差异是前景内容与色温**：冷龛叠加 `linear-gradient(180deg, rgba(22,192,182,.10), transparent)`，暖龛叠加 `rgba(217,142,50,.12)`

#### 2.2.3 3D 资产的加载时机（**首屏之后**才发生）

| 阶段 | 加载内容 | 体积 | 触发 | 备注 |
|---|---|---|---|---|
| **首屏（角色选择）** | **无** | **0 bytes** | — | 不加载 three.js / R3F / 任何 GLB / SPZ |
| 选定角色 → 进街区 | 玩家 Avatar GLB | **3MB** | 进入街区时 | 一次，之后全程复用 |
| 靠近某摊位（≤26m，现有 LOD 阈值） | **单个** HR GLB | ≈1.8MB | 距离触发 | 现有 `HRStand` 的 NEAR/FAR LOD 逻辑已是按需，**但 `preloadHRModels()` 会预载全部 9 个（16MB）→ 必须改为按需**（见 R11） |
| 远景 HR | 占位低模（程序化，现有 `PlaceholderHR`） | 0 | — | 已有实现，不动 |
| 点击门面进办公室 | **单个** SPZ | ≈4.2MB | 点击时 | 4 套 17MB 不整包进，必须单套懒加载 + 加载态（见 R12） |
| 作品集 / 求职者形象 | 求职者 GLB 或预置回放产物 | ≤2MB | 进入求职者空间时 | 见 §3.2 通道 |

> **首屏预算实测口径**：首屏网络请求中**不得出现** `.glb` / `.spz` / `.ktx2` / `.ply` 任一扩展名。这一条可直接用 DevTools Network 面板 type 过滤验证，写进 §9 验收清单。

#### 2.2.4 降级三档（**零资产前提下，档位大幅简化**）

| Tier | 触发条件 | 表现 |
|---|---|---|
| **A · 完整动效** | 默认 | 粒子呼吸 + 作品卡浮动 + 轨道节点游走 + 日月辉光 |
| **B · 精简动效** | `prefers-reduced-motion: reduce` | 全部循环动画停止，保留各自"当前帧"构图；轨道节点停在等分位 |
| **C · 纯静态** | 极旧浏览器（无 CSS `transform` 动画支持） | SVG 静态首帧 + 无暗角动画 |

- **三档都不需要任何额外资产**（SVG 本身就是矢量），因此**不存在"降级到图片"的资产缺失风险**。
- 降级不改变布局、文案、对比度、Tab 序。
- 由于不再有 WebGL 帧率采样，**Tier 判定改由 `prefers-reduced-motion` + `navigator.hardwareConcurrency ≤ 4` 一次判定**，入场即定，不做运行时切换（零抖动）。

#### 2.2.5 程序化 WebGL 预览（**已正式撤回 · 本期不做**）

> **主理人 2026-10-27 追认**：本条由「可选增强」改为「**撤回**」。原判断"首屏有真 3D 在动是逛厂 vs 表单 App 的分水岭"**不成立**——推翻它的是三条事实：

| # | 事实 | 推论 |
|---|---|---|
| 1 | three.js + R3F 进首屏 bundle ≈ **600KB gzip** | 即使 0 资产，体积也已经付掉了，却换不到任何 3D 内容（程序化剪影 ≠ 真场景） |
| 2 | iOS Safari 的 **WebGL 上下文内存上限**是真实约束；多一个上下文 = 多一个崩溃面 | 首屏多一个上下文，收益是"炫"，代价是"可能打不开" |
| 3 | 选完角色 **2 秒后**就进真 3D 街区 | 第一印象在那 2 秒已经建立，首屏的"炫"是冗余的 |

**结论**：首屏 SVG 舞台是**唯一方案**，不存在"三龛 / 双龛 / 单龛 / WebGL 龛"的分档。§2.2.4 的降级三档只针对 `prefers-reduced-motion` 与低配设备，**不涉及资产与 WebGL**。

> **"降级成图片这一步根本不存在"** —— 这是 SVG 相对 3D 预览最大的结构性优势：SVG 是矢量的，最坏情况就是它自己静止；没有资产管线、没有预渲染步骤、没有 `THREE.WebGLRenderer` 的 context lost 风险。
> 若未来（产品期、非 Demo）确需首屏 3D，正确做法是**独立首屏路由 + 独立 bundle**（首屏 chunk 不含 three.js），而不是把它塞进当前主 chunk。**本规格不为此预留设计。**

### 2.3 两张角色卡的视觉区分手段（**重点**）

#### 2.3.1 设计立场：不能只靠"文字 + 图标"

评审要求"玻璃孪生体式的差异化表达"。本方案的区分是**五重编码**，任意去掉两重仍可辨识（满足 WCAG 1.4.1 非颜色编码）：

| # | 编码维度 | 求职者侧 | HR 侧 |
|---|---|---|---|
| 1 | **形状** | **环形**（轨道 + 节点） | **立柱**（碑形 + 光条） |
| 2 | **预览龛内容**（SVG） | 环形轨道 + 数据粒子 + 3 片作品玻璃卡 | 悬浮钞票山 + 参数碑缩影 + 头顶日月 |
| 3 | **冷暖光** | 冷光（`--role-candidate-emissive` 粒子 + 冷色温层） | 暖光（`--role-hr-emissive` 钱山 + 暖色温层） |
| 4 | **色相** | `--role-candidate-accent` / `accentDark`（冷青） | `--role-hr-accent` / `accentDark`（逛厂币橙） |
| 5 | **文字** | 「我是求职者」/「逛厂看公司，不看广告」 | 「我是 HR」/「让参数被看见，不被质疑」 |

#### 2.3.2 为什么角色色**不复用行业四色**

> **风险**：若求职者用互联网蓝、HR 用智造橙，会建立"求职者 = 互联网行业 / HR = 智造行业"的错误暗示，与产品的四行业街区直接矛盾。

因此角色色为**新增语义色**，且刻意避开行业四色 + 品牌红金的色相带：

| 角色色（**3D 发光基色**） | 与最近的四色/品牌色距离 | 理由 |
|---|---|---|
| `--role-candidate-emissive` = `#16C0B6`（青，hue 176°） | 距互联网蓝 `#4a9eff`(213°) 37° | 冷调 = 数据/技术/成长 |
| `--role-hr-emissive` = `#d98e32`（橙，hue 34°） | 距智造橙 `#f0883e`(25°) 9° | **有意复用"逛厂币橙"**（与 `color.scene.billOrange` 同值）→ HR 侧 = 钱的颜色；两者不同屏（首屏 vs 街区），不构成混淆 |

> **v1.2 拆分说明**：上表是**色相谱系**（决定"这两个角色在色彩上属于哪一族"），实际令牌已拆为两组——
> **UI 图形色**（`accent` / `accentDark`，双模，配玻璃容器）与 **3D 发光色**（`emissive`，单值，配描边）。
> 拆分的原因见 §2.6.2 B′：同一个 `#16C0B6` 在 UI 玻璃上要 7.75:1（用亮变体）、在 3D 场景里只有 1.85:1（用自发光 + 描边），**一个色值无法同时满足两种落点**。

> **角色色永不承载白字**（同行业色规则）。角色色只用于：描边、图标、粒子、数据体、≥24px 图形元素。见 §2.6.3。
> **例外（v1.2）**：**暗变体**（`accentDark` / `hrUiDark`）作填充底时**必须配白字**（5.97 / 6.21:1），配墨字只有 3.10–3.22:1 ❌。

#### 2.3.3 预览龛的视觉参数（**纯 SVG / CSS，可执行数值**）

> 全部数值为 SVG 用户单位（viewBox `0 0 320 200`），1 SVG 单位 = 1.60m ÷ 120 ≈ **0.0133 m**。换算标注在括号里。

- 全部动画只用 `transform` / `opacity`，**禁止动画 `width`/`height`/`cx`/`cy`**（会触发 SVG 重排）

- 龛内 SVG 在 `prefers-reduced-motion` 下降为静态（见 §2.2.4）

- 粒子最内圈距剪影身体 ≥ 6 SVG 单位（**0.08m ≥ 0.02m** ✅）
- 作品卡内缘距剪影 ≥ 5 SVG 单位（**0.067m ≥ 0.02m** ✅）
- 钞票山最近边距剪影 ≥ 6 SVG 单位（**0.08m ≥ 0.02m** ✅）
- 头顶要素底边距头顶 ≥ 3 SVG 单位（**0.04m ≥ 0.02m** ✅）

#### 2.3.4 玻璃浮层的「实底 + 玻璃」双层（**全局配方修正**）

> **v1.2 升级**：本条原为「首屏角色卡的一个修正」，主理人 2026-10-27 拍板**升级为全站强制修正**——因为缺陷不在"角色卡"，而在"v4 主题反相后的玻璃配方"本身。

##### 2.3.4.1 发现（v4 玻璃配方的系统性缺陷）

ui-system-v3 §6.2 的玻璃配方是**单层 `rgba(255,255,255,.82→.60)`**，为夜景设计。v4 twin 把 UI 玻璃在浅色主题反相成深玻璃 `rgba(11,14,26,.72)` 后，若**不垫实底**，实测对比度如下：

| 主题 | 合成底（玻璃 .72 与场景地平线合成） | ink-primary | ink-secondary | ink-muted |
|---|---|---|---|---|
| 浅色 | `#4C5059`（L=0.0806） | `#e6edf3` 6.84:1 ✅ | `#b7c2cc` **4.46:1 ❌** | `#b0bcc8` **4.18:1 ❌** |
| 深色 | `#BFC2CA`（L=0.5382） | `#0b0e1a` 10.79:1 ✅ | `#39414d` 5.78:1 ✅ | `#454c59` 4.85:1 ✅ |

> **准确的结论（v1.2 更正，详见 §2.6.2 A′）**：真正不达标的**只有浅色主题**——次级文字 4.46 ❌、muted 4.18 ❌；**深色主题本来就全部达标**。
> v1.0/v1.1 写的"两个主题的次级文字都掉到 4.5:1 以下（4.44 / 4.46）"**不准确**：那是因为当时误用了**页面底色域**的 `color.text.secondary`（`#4A5160`）而不是玻璃浮层实际使用的 `--ui-ink-secondary`（深色主题 `#39414d`）。**结论方向不变（垫实底仍必要），但范围比原先声称的窄。**

**这不是"角色卡没做好"，而是"任何浮在 3D 场景上的玻璃浮层都没做好"**——名片卡、HUD、导航器、抽屉、toast 全中招，因为它们共用同一个 `--ui-glass-fill`。

##### 2.3.4.2 影响面（**全部要垫实底**）

| # | 浮层 | 承载内容 | 修正后配方 | 特别要求 |
|---|---|---|---|---|
| 1 | **名片卡** `GcCompanyCard` | 公司名 / 职位 / 参数数值 / 认证章 | 垫 `--ui-glass-underlay` + 保留玻璃面 | 数值（`num` 26px）属大字，但统一垫底，避免数值在亮场景上"发飘" |
| 2 | **HUD** | 我的进度：Lv / XP / 投递数 / 对比篮 / 已参观 / 四区 pips | 垫底 | HUD **绝不出现**任何单家参数或公司名（ux §3.4.3）；pips 是图形，不受文字约束 |
| 3 | **导航器**（四臂罗盘 + 四区进度行） | 臂上文字标签 | 垫底 | 窄条 + .86 实底会让罗盘显厚 → **臂内标签一律用 ink-primary**（不依赖底色），但仍垫底以免边缘糊进场景 |
| 4 | **对比篮坞** | 2 家公司并排 + 各项数值 | 垫底 | 并排对比是"精确读数"场景，底色稳定性要求最高 |
| 5 | **演示控制台** | 模式切换 / 演示直入 / 回放控制 | 垫底 | 控制台内的"演示形态切换"等按钮文字 ≥4.5:1 |
| 6 | **抽屉**（参数面板 / 详情板 / 访客模式提示条） | 长文本 + 表单 + 数值 | 垫底 | 输入框**另需自身 1px 边框**（边框是 WCAG 1.4.11 非文本对比要求，不靠底色兜） |
| 7 | **toast** | 一句话反馈 | 垫底 + **关闭 saturate 提升** + 1px 内描边 | toast 浮在最上层、背后是动态 3D，必须最锐利；文案一律短句（ui-system-v3 §7.1 反馈收敛） |

> **新增的玻璃浮层一律按此配方**，不需要再逐个讨论。

##### 2.3.4.3 工程实现：新增 `--ui-glass-underlay`，`--ui-glass-fill` 语义不动

> **工程约束（主理人指定）**：`--ui-glass-fill` **保持不动**（避免改动 v3 既有变量语义导致存量代码回归），另起 `--ui-glass-underlay` 承载"实底"。

```css
/* 全局玻璃浮层基类 —— 只加一行 background-color，不动既有 background */
.gc-glass {
  background: var(--ui-glass-fill);            /* ← 既有写法，语义不变 */
  background-color: var(--ui-glass-underlay);  /* ← 新增实底；必须写在 background 之后 */
  backdrop-filter: blur(28px) saturate(180%);
  -webkit-backdrop-filter: blur(28px) saturate(180%);
}
```

| 规则 | 说明 |
|---|---|
| **书写顺序** | `background-color` **必须**在 `background` 简写**之后**——`background` 简写会重置 `background-color`，写反了实底会被清掉（这是本条最容易踩的坑，已进 §9.5 checklist） |
| **取值** | 浅色主题 `rgba(11,14,26,0.86)`；深色主题 `rgba(255,255,255,0.86)`（唯一值，不做分档） |
| **反相规则** | 与 §1.3 主题反相表一致：浅色主题深底 + 白字，深色主题亮底 + 墨字。**实底必须与玻璃面同相位**，不能出现"深玻璃 + 亮底" |
| **不变量** | `--ui-glass-fill` 的值、模糊半径、饱和度、内高光、双层阴影**全部不改**；本条只增加一层 `background-color` |

**为什么这个配方成立（CSS 合成顺序）**：`backdrop-filter` 采样的是**元素下方**的绘制结果，而 `background-color` 绘制在元素自身、与背景图同层。合成后 = 模糊背景 → 实底（86%）盖上 → 玻璃渐变高光（12–18% 白）→ 内容。**透射率 = 14%**。

##### 2.3.4.5 代价与补偿：通透感到底损失了多少

诚实地说：垫 .86 实底后，**"看穿"变成了"看出一片色"**。但这不是真的牺牲玻璃感——

| 维度 | 修正前（单层 .72 玻璃） | 修正后（.86 实底 + 玻璃面） | 结论 |
|---|---|---|---|
| 透射率 | 28% | **14%** | 28% 时能读出背景"轮廓"（正是这个轮廓让文字不达标）；14% 时只能读出"一片色块"——**背景细节本来就已经读不出了** |
| 模糊可感知度 | 背景有明显结构 → 模糊明显 | 背景无结构 → 模糊表现为"色彩揉成一片" | 玻璃的"揉色"感保留 |
| 厚度感 | 靠内高光 + 阴影 | 靠内高光 + 阴影 + **实底带来的"面板感"** | **更强**（实底让浮层从"贴纸"变成"舷窗"，正好强化 OCC-1 的高光叙事） |
| 文字可读性 | 浅色主题次级 **4.46** ❌ / muted **4.18** ❌ | **7.37 / 6.90** ✅ | 核心收益 |

> **一句话**：垫实底牺牲的是"背景可辨识度"——而那恰恰是造成文字不达标的原因本身。玻璃感的真正来源（揉色、内高光、厚度投影）一条没少。

**三条结论**：

1. **浅色主题：不达标区不是"边缘情况"，是常见情况。** UI 玻璃浮层（顶栏 / HUD / 名片卡 / toast / 抽屉）恰恰贴着画面上方与远处地平线——那是全场最亮的一带。凡浮在亮背景上的次级文字与脚注，**必不达标（4.18–4.47）**。
2. **深色主题：全部达标，但最差一档 muted 只有 4.55:1，余量 0.05。** 这意味着**任何对玻璃 alpha 的微调都可能把它推下 4.5**（例如为了更强的玻璃感把 `.72` 改成 `.70`）。**结论：两个主题都要垫实底**——深色主题是为了**留余量**，浅色主题是为了**达标**。
3. **垫实底后（`--ui-glass-underlay` = .86）**：浅色最坏情况合成底 `#2b2f3a` → **11.29 / 7.37 / 6.90 ✅**；深色最坏情况 ≈`#dee0e4` → **14.58 / 7.81 / 6.55 ✅**。**垫实底就是把"与背景相关"变成"与背景无关"的那一步。**

> **顺带解释一处现存注释**：`web/src/styles.css:34` 写着"白天深玻璃合成底 ≈ rgb(64,69,80)"——反推其假设背景 ≈ `#c8d2db`（**中上天空**）。在那个假设下确实全部达标（secondary ≈5.0 / muted ≈4.7）。**代码没错、验算也没错，错的是把"中上天空"当成了"唯一背景"。** 玻璃是浮在场景上的，场景不只有一种亮度——**验收必须按最坏背景算**。

> **最小代价的替代方案（不推荐，但列出以免有人重新发明）**：把浅色主题的玻璃 alpha 从 `.72` 提到 `.75`，最坏情况即可达标（secondary 5.04 / muted 4.72）。但它只解决"玻璃直接压在场景上"的情形，**不解决"玻璃叠玻璃"**（名片卡叠在 HUD 上时，底是另一块半透明玻璃），且余量仍然很薄。**全局垫实底是唯一一处修好的方案。**

|---|---|---|---|---|
| **P1 自动分割** | 人像分割模型（可选，如 MediaPipe selfie segmentation） | **本期默认不启用** —— 需打包 ~3MB wasm，与"首屏 5MB + 不引运行时第三方"两条硬约束冲突，且小模型在侧脸/逆光下会撕裂 | — | 体积 + 失败率 |
| **P2 椭圆蒙版（默认）** | 以人脸框（可用浏览器 `FaceDetector`；不可用则用**固定构图 + 用户手动对齐**）为中心生成椭圆 alpha 遮罩 | 默认 | 椭圆半轴比 **rx 42% / ry 52%**（相对 512 画布，即 215 / 266 px）；**羽化 14px**（8–24px 可调） | 头发/肩膀会切掉一部分 |
| **P3 圆角矩形蒙版** | 用户手动把 P2 切成"圆角矩形"（更适合正面照） | P2 结果不佳时 | **圆角比 34%**（= 0.34 × 512 ≈ 174px），羽化同上 | 裁切感更强 |
| **P4 用户自绘** | 面板内提供"涂抹保留区域"（笔刷 12px，保留/擦除两态） | P2/P3 都不满意时 | 同上 | 需要额外的交互（本期可选实现） |

> **绝对禁止**：把未处理的整张照片矩形直接贴在头部位置。这是**社死级失败**——一旦评审看到，方位角就毁了。

**羽化的实现要点（易踩坑）**：`alphaTest` 是**二值**的，会把 14px 羽化带直接砍成硬边。因此面片**必须双层**：

| 层 | 作用 | 材质 |
|---|---|---|
| 内层 · 硬轮廓 | 保证遮挡正确（不穿模） | `alphaTest 0.5`，`transparent: false` |
| 外层 · 柔边 | 保留羽化，消除锯齿 | `transparent: true`，`depthWrite: false`，`renderOrder` +1 |

> 只用单层 + `alphaTest` 的实现**看起来"贴纸感"极强**——因为剪影边缘是硬折线，违反 OCC-3「边缘描边同源」。

##### 3.2.1.2 直方图调色映射（**只统计蒙版内像素**）

> **第一条原则**：统计范围 = **蒙版内像素**。用整张照片做直方图会被背景（白墙、天空、深色房间）污染，把脸调黑或调亮。

| 步骤 | 公式 / 参数 | 说明 |
|---|---|---|
| ① 统计 | 取蒙版内像素的 **p05 / p50 / p95** 分位数（**不用 min/max**，避免离群值） | 在**线性空间**统计（sRGB → 线性） |
| ② 亮度归一 | 目标 `p50 → 0.52`（线性）；斜率 `slope = 0.42 / max(0.06, p95 − p05)` | 保证脸既不发黑也不过曝 |
| ③ 对比增益 | `contrast = clamp(0.42 / (p95 − p05), 0.80, 1.60)` | 平淡照片提对比，HDR 照片压对比 |
| ④ 总增益 clamp | `gain = clamp(slope × contrast, 0.85, 1.15)` | **与 v1.0 一致**：增益过大会让贴片与场景光照不匹配 |
| ⑤ 输出 | `map` = 调色后的 512² 贴图（`CanvasTexture`，`colorSpace = SRGB`）；材质 `roughness 0.55`、`metalness 0` | **照片不是玻璃**——不要套玻璃材质，否则脸会"糊"成一块 |
| ⑥ 场景匹配 | 面片材质额外叠一层 `emissive` = 场景环境色的 12%（取 `theme.*.hemiSky`），`emissiveIntensity` 0.35 | 让脸吃进场景光，不显得像贴纸 |

**肤色保护（避免把脸染绿）**：

| 保护项 | 规则 | 目的 |
|---|---|---|
| 肤色判据 | 转换到 **YCbCr**，判据 `77 ≤ Cb ≤ 127` 且 `133 ≤ Cr ≤ 173` | 经典肤色椭圆，覆盖各人种 |
| 占比闸门 | 若蒙版内肤色像素占比 **< 12%** → 判定为"极端光照 / 非人像" → **完全关闭色度调整**，只做亮度归一 | 宁可欠调，不可染绿 |
| 亮度系数 | 肤色像素的亮度调整量乘 **0.5**，非肤色像素乘 1.0 | 脸不会被整体压暗 |
| 色度系数 | 色相偏移量对肤色像素乘 **0.25**，非肤色像素乘 1.0 | 背景可以偏色，脸不行 |
| 硬上限 | 总色相偏移 **≤ 6°**；饱和度偏移 **±0.08** | 任何情况下不出现"绿脸/紫脸" |

> **肤色保护是这条路径的成败关键**：一张在日光下拍的白衬衫背景照，如果直接做全局直方图拉伸，衣服会把整张脸的色温拉偏。**先判肤色、再按肤色分区调**——这是与"全局滤镜"的分界线。

##### 3.2.1.3 贴入的几何与材质

| 项 | 规格 |
|---|---|
| 面片尺寸 | 0.30 (W) × 0.36 (H) m（贴合头部），**双层共面间隙 0.002m** |
| 面片背面 | 补一张同色**薄板**（厚 0.01 m，`--role-candidate-accent` @0.35 玻璃），避免从侧面看是"一张纸" |
| 相机贴片 shadow | 面片后方 **0.02 m** 处放一张 `shadowTexture()` 投影片，保证"贴上去"而非"浮着"（遵守 0.02 m 间隙铁律） |
| 跟随 | 面片与头部 mesh 同挂点，随头部动画运动；B 类参数（气质风格）重生成时整体替换 |
| 用户可见说明（必须常驻，面板底部 12/18 ink-secondary） | 「照片在浏览器本地处理，不上传、不留存。这是把你的照片贴进 3D 形象；完整的 Lux3D 风格化重建需要本地脚本或后端。」 |
| 与 A 类参数联动 | 贴入后仍可实时调发型/服装/主色/体型/肤色（§3.3），照片面片跟随头部 mesh 一起动 |

#### 3.2.2 生成通道（Generation Channel）抽象 —— **等待态与数据源解耦**

> 核心设计：**等待态的视觉、阶段叙事、进度算法、失败处理、退出机制 100% 复用**，只有"数据从哪来"不同。这样将来接上后端时，**一行 UI 代码都不用改**。

| 通道 | 触发条件 | 数据源 | 阶段推进 | 产物 | 本期是否可用 |
|---|---|---|---|---|---|
| `replay` **演示回放** | **当前静态 Demo（默认）** | 本地预置 manifest（`web/public/assets/demo/avatar-gen/*.json`：含产物 GLB 路径、真实耗时、阶段时间轴） | **本地时间轴驱动**（压缩播放，见下） | 预置的**真实**生成产物 | ✅ **本期唯一可用** |
| `local` 本地脚本 | 用户本机跑 `tools/gen_avatar_from_photo.py`（本地已通） | 轮询本地脚本输出目录 | 真实进度 | 真实 GLB | ⚠ 需后端代理暴露状态；**不可作为 Demo 主路径** |
| `live` 实时 API | 部署了后端代理（未来） | 轮询 API | 真实进度 | 真实 GLB | ❌ 本期不做（Key 不能进前端） |

**`replay` 通道的三条诚实规则**：

1. **必须挂「演示回放」徽标**：等待态顶部一枚 chip「**演示回放** · 真实链路需运行本地脚本 `tools/gen_avatar_from_photo.py`」，`--role-hr-accent` @0.14 底 + 墨字 12/18 600，**不隐藏、不折叠**。
2. **压缩播放，但剩余时间给真实值**：
   - 真实耗时按实测 **85s**（76–108s 区间中位）先验计算；
   - 回放时进度条**按 4.2× 加速**推进（85s → 20.2s 播完），并在角标标注「演示已加速 4.2×」；
   - **剩余时间显示的是真实剩余**（「真实链路还需 00:41」），让观众感受到"这东西真的要等一分多"，而不是"20 秒就到头了"的错觉；
   - 角标位置固定在进度条右上，不抢主文案的视觉层级。
3. **完成页必须标注**：结果页顶部一行 12/18 ink-secondary「此为预置的真实生成产物（回放），非本次即时生成」。

#### 3.2.3 回放通道的分阶段文案与进度映射

进度条总长映射到**真实 85 秒**；回放播放时按 4.2× 加速推进，进度条上的百分比**始终对应真实耗时比例**。

| 阶段 | 真实时间窗 | 进度映射 | 阶段标题（16/24 600） | 阶段副文（13/20 500） |
|---|---|---|---|---|
| **P1 取材** | 0–6s | 0% → 10% | 正在读取照片 | 提取面部特征与轮廓 |
| **P2 建模** | 6–48s | 10% → 72% | 正在生成 3D 网格 | 风格化卡通 · 保留你的辨识度 |
| **P3 绑定** | 48–78s | 72% → 94% | 正在绑定骨骼 | 生成 8 秒待机动作 |
| **P4 载入** | 78–85s | 94% → 100% | 正在载入街区 | 压缩与优化，预计 2.2MB |

> **非线性映射的用意**：P2 独占 42 秒却只占 62% 的进度条——这是对的，因为真实耗时就在那里。真正的防"卡死感"来自**阶段文案 + 视觉叙事**（下节），而不是把进度条做快。

#### 3.2.4 等待态的视觉叙事（每阶段一个"看得见在动"的主体）

> **舞台 = 单个 320×320 的 Canvas 2D**（**不是 WebGL**）——等待态本身零 3D 资产。Canvas 2D 画这四段绰绰有余（320 个粒子在 2D canvas 上几乎零成本），且不占首屏预算（此阶段已在街区内）。

| 阶段 | 视觉主体 | 具体做法 |
|---|---|---|
| P1 | **扫描取景框** | 320×320 取景框（四角 8px L 形定位角标，`--role-candidate-accent`），一条 2px 青色扫描线自上而下循环，周期 **1.6s**，扫描线带 24px 柔光拖尾 |
| P2 | **粒子收敛 + 轮廓描边** | 320 个点（size 2px，`--role-candidate-accent`）从随机云向"头肩剪影"的 220 个目标点收敛（lerp 系数 = 阶段进度）；同时一条 SVG 剪影轮廓用 `stroke-dashoffset` 从 100% → 0%（描边 2px，线宽 1.5） |
| P3 | **骨骼逐点点亮** | 12 点简化骨骼（头/颈/双肩/双肘/双腕/髋/双膝），按绑骨顺序每 120ms 点亮一个；每点 `scale 1 → 1.6 → 1`，320ms |
| P4 | **线框旋转淡出 → 3D 结果** | 线框整体转 90° 并淡出（240ms，`cubic-bezier(.4,0,1,1)`），随即交叉淡入**真实 3D 预览**（此时玩家 Avatar / 结果 GLB 已在场景内，WebGL 已就绪） |

### 3.3 个人参数 → 形象具象化映射表

##### 3.3.0 参数的准入判据（**Phase 2 裁定回写 · ux C1**）

> **ux-ui-designer 裁定（2026-10-27）**：**外观参数不进词典。** 理由：外观是「**资产装配**」（asset assembly），不是「**招聘参数**」（recruiting parameter）——词典的职责是"HR 能读懂并据此做决策的信息"，发型/服装/主色/配饰/体型/肤色不在其中。
> **Phase 1 采纳该裁定，并采纳其"四要素判据"写进团队规范。**

| # | 要素 | 判定标准 | 外观参数 | 招聘参数 |
|---|---|---|---|---|
| 1 | **词典词条** | `dictionary/candidate-dictionary.json` 中能查到条目 | ❌ 无 | ✅ `expected_salary` / `portfolio_gallery` / `credential_order` |
| 2 | **mapping type** | `dictionary.schema.json` 的 `mapping.type` enum 有对应值 | ❌ 无（需扩 enum） | ✅ `salaryCloud` / `gallery` / `nameplate` |
| 3 | **3D 载体** | 场景里有一个可指认的几何 | ✅ mesh / 挂点 | ✅ |
| 4 | **可见性分级** | L0 / L1 / L2 明确 | ✅（本地，无隐私问题） | ✅（L0 档位 / L1 精确值） |

> **四个要素缺一，就不做这个参数。** 这条判据的价值在于：它把"要不要加一个新参数"从"好不好看"变成"能不能被 HR 读懂并决策"。

**对本规格的三条硬约束**：

| # | 约束 | 后果 |
|---|---|---|
| 1 | §3.3 表中的**外观六项**（发型 / 服装 / 主色 / 配饰 / 体型 / 肤色）与 **B 类气质风格**一律标注为「**资产装配项（非词典参数）**」 | **不进 `dictionary.schema.json`**、**不在 HR 侧参数表单出现**、**不可被公司检索** |

#### 3.4.1 环绕排布

| 要素 | 规格 |
|---|---|
| 轨道中心 | 求职者脚下（y=0） |
| 主轨道半径 | **2.20 m** |

#### 3.4.2 单件作品的载体形态（**由作品类型决定，形状本身即编码**）

| 作品类型 | 载体 | 几何 | 材质 |
|---|---|---|---|
| 平面作品（UI / 插画 / 摄影） | **玻璃卡**（矩形） | 0.62 × 0.44 × 0.02 m | `opacity .78`，`roughness .10`，`metalness 0`，图像作 `emissiveMap`；顶部 12% 亮带（内高光）；描边 `--theme-* wire` @0.5 |
| 项目卡片（代码仓库 / 链接） | **全息板**（方形） | 0.50 × 0.50 × 0.01 m，双面 | 中心 0.22m 发光图标（仓库 / 星标，内联几何）；底部 0.04m 高"star 计数灯条"（每 1k 一格，≤10 格，`--color-brand-gold`）；`opacity .55`，无背板 |
| 3D 作品 | **实体展台**（圆形） | 玻璃圆台 Ø0.60 × 0.28 高 + 上方作品缩模 | 圆台 `opacity .62`（同 twin 玻璃体）；台面下沿一圈 `--theme-* wire` @0.5 环 + 接触阴影 |

> **形状即编码**：卡片 = 矩形，项目 = 方形，3D = 圆形 —— 即使全部去色，剪影仍可区分三类作品。

#### 3.4.3 缓动与轨道运动

| 状态 | 运动 | 时长 / 缓动 |
|---|---|---|
| 常态 | **作品不动**，各自呼吸浮动 ±0.012m（Y 轴），周期 3.2s，相位 = index × 0.18s | 无限循环 |
| 玩家进入 1.2m 内 | 该作品沿**径向**推出 0.35m，并转向正对玩家 | 320ms `cubic-bezier(.22,1,.36,1)` |
| 玩家离开 | 回收原位 | 320ms 同上 |
| 走近聚焦（转场） | ① 作品推出 320ms → ② 相机对准 420ms `cubic-bezier(.4,0,.2,1)` → ③ 详情扇板 `scale .94→1` + `opacity 0→1` 280ms | 见 §5.1 |
| 作品塔散开（玩家进入塔 1.8m） | 塔内作品散回环 | 600ms `cubic-bezier(.22,1,.36,1)` |

> **为什么作品不整体自转**：环绕自转会让作品"跑过"玩家眼前，无法阅读。正确模型是**作品静止、人动**（产品已定"走近自动聚焦"，见词典 `portfolio_gallery.focusOnApproach = true`）。自转只保留给首屏预览龛里的粒子（0.32 rad/s）。

#### 3.4.4 降级

| 条件 | 降级 |
|---|---|
| 移动端 / `deviceMemory ≤ 4` | 只渲染**最近 6 件** + 1 座作品塔 |
| 作品总数 > 16 | 塔合并（§3.4.1） |
| `prefers-reduced-motion: reduce` | 取消呼吸浮动与推出动画，作品固定；聚焦改为直接切换 |

### 4.3 参数碑 ↔ 悬浮三件套：明确分工（**不造两套同义东西**）

#### 4.3.1 现状问题

项目里已经存在两套表达同一组参数的载体：
- `HRStand` 内的**参数悬浮三件套**（钱捆堆 / 切口牌 / 头顶日月）
- `StreetScene` 内的**参数碑**（碑高=总包 / 5 灯条=五险 / 顶灯=下班）

两者语义重叠。本规格**不推翻任何一个**，只做**场景分工 + 同屏互斥**。

#### 4.3.2.2 参数的计算时机：快照 vs 实时（**Phase 2 裁定回写 · ux C5**）

> **裁定**：**滑杆只驱动「建厂预览」与「对比页」两处**。街区里的 64 个摊位是**已发布快照**，参数**只在加载时算一次**，之后不再重算。

| 场景 | 参数来源 | 是否实时 | 理由 |
|---|---|---|---|
| **招聘街区 · 64 摊位** | 已发布快照（加载时算一次，`useMemo` 缓存） | ❌ | draw call 红线 ≤200；实时重算 64 摊位的参数几何 = 每帧重建 → 必爆 |
| **HR 建厂预览** | 滑杆实时驱动 | ✅ | 只有 1 个摊位，无密度问题；这是"参数 → 实物"的唯一现场演示位 |
| **对比页 / 对比篮坞** | 滑杆实时驱动 | ✅ | 只有 2 家，无密度问题 |
| **作品廊 · 我的展位** | 已发布快照（发布时冻结） | ❌ | 同上；访客进入时读快照，不读作者当前的滑杆值 |
| **作品廊 · 他人展位** | 对方的已发布快照 | ❌ | **访客永远看不到对方"正在拖的滑杆"**——那会变成实时围观 |

**实现规则**：

```text
lotSnapshot = useMemo(() => ({
  totalPackage: totalPackage(lot.params),
  socialInsuranceBaseRatio: lot.params.socialInsuranceBaseRatio,
  offworkTime: lot.params.offworkTime,
  version: lot.version,          // 发布时冻结的版本号
}), [lot.id, lot.version]);       // ← 依赖项里没有 params 对象
```

| 规则 | 说明 |
|---|---|
| **依赖项必须是 `version` 而不是 `params`** | 否则任何参数对象变更都会触发重算 → 实时化 → draw call 爆 |
| **滑杆变化只写预览场景** | 不广播、不通知场景其余部分；预览场景里也只有 1–2 个摊位参与重算 |
| **发布 = 冻结点** | Step 5 发布时把当前参数值写入 `lot.params` 并递增 `lot.version`，此后快照不变 |
| **作品廊同理** | 求职者的展位参数在"发布展位"时冻结；访客进入读快照 |
| **作品廊 · 他人展位** | 访客永远看不到对方"正在拖的滑杆"——那会变成实时围观 |

> **这条规则同时是视觉规则**：因为碑高与悬浮物尺寸**读同一个冻结对象**，§4.3.5 的同屏互斥在快照模式下**必然稳定**——不会出现"碑已经变了、悬浮物还是旧值"的半帧不一致。
> 反过来说：**如果实现里碑和悬浮物分别各自订阅 `params`，就会出现一帧内两种数值**——这正是 ux 验收项 D8 要拦的东西（见 §4.3.5）。

#### 4.3.3 为什么这样分（三条论证）

1. **距离决定精度需求**：远看只需要"谁高谁低"（相对比较）→ 碑的连续高度够用；近看才需要"切开在哪、几点下班"（精确语义）→ 悬浮物的形状才表达得了。
2. **密度决定成本**：64 摊位 × 3 个悬浮体 = 192 个动态物体，远景全开会爆 draw call；碑是 4 个 InstancedMesh 解决 64 摊位的表达。悬浮物只在近景（相机 12m 内最多 3–4 个摊位）存在，成本可接受。
3. **语义不重叠**：碑是"这家公司"的**固定标识物**（像门牌），悬浮物是"这家公司"的**随身读数**（像仪表）。两者在叙事上是"牌子 + 手持仪表"，不重复。

#### 4.3.4 位置不冲突

- 参数碑在摊位**左后**方（现有 `lx=-1.05, lz=-0.55`）。
- 悬浮三件套绕 HR（摊位中心，HR 在 `[0, 0.14, 0]`），最内缘 0.60 m。
- HR 身体与碑体的水平距离 = √(1.05² + 0.55²) = 1.19 m > 碑截面半宽 0.15 + 身体半径 0.22 = 0.37 m → 间隙 0.82 m ✅

#### 4.3.5 同屏互斥规则（三态滞隐，**必须实现**）

以 lot 中心到相机的距离 `d` 判定（滞隐带 2 m，防抖）：

| 距离 d | 参数碑 | 悬浮三件套 |
|---|---|---|
| d > 14 m | 显示（opacity 1） | 隐藏 |
| 10 m ≤ d ≤ 14 m | 交叉淡化（碑 1→0，三件套 0→1，300ms） | 同 |
| d < 10 m | 隐藏（opacity 0，保留占位不卸载） | 显示 |

- 实现：`HRStand` 现有的 `near/far` 滞回逻辑（NEAR=26 / FAR=34，控制 GLB 切换）**不动**，另加一组独立的 10/14 m 阈值用于显隐，二者互不干扰。
- 交叉淡化期间两者**不同时达到 1.0**，保证任一帧上"同一个数字只有一个形态"。


> **这是本节的核心交付**：解决"参数碑与悬浮物同义重复"，而不是再增加第四种表达。

#### 4.3.5.1 D8 硬验收（**Phase 2 验收项回写 · ux D8**）

> **D8**：**交叉淡化期间，任一帧上同一个参数不得出现两种形态。**

| 项 | 要求 | 可机检方式 |
|---|---|---|
| 数值一致 | 碑面高度、钱捆堆层数、切口牌缺口、顶灯色**读同一个冻结对象**（§4.3.2.2） | 断言 `stele.total === trio.total` |
| 形态唯一 | 任意一帧内，同一参数至多有一个载体 `opacity > 0.02` | 遍历该 lot 的两套载体，断言 `(a.opacity > 0.02) && (b.opacity > 0.02)` 为假 |
| 交叉淡化单调 | 淡化期间碑 opacity 单调 ↓、三件套 opacity 单调 ↑（300ms 内不回头） | 采样 20 帧，断言单调 |
| 任何参数 | 总包 / 五险基数 / 下班时间 **三者逐项校验**，不是抽查一项 | 遍历 3 个参数 |

#### 4.3.5.2 R4 例外：建厂预览时允许同屏（**唯一的例外，且有条件**）

> **Phase 2 裁定（ux R4）**：**建厂预览时允许参数碑与悬浮三件套同屏**（预览里只有一个摊位，不存在密度问题），但此时**参数碑降到 40% 透明度**，作为"对齐参考"。

| 项 | 街区常态 | **建厂预览（R4 例外）** |
|---|---|---|
| 碑 | opacity 1 / 0（按距离三态） | **固定 0.40**（不随距离变） |
| 三件套 | opacity 0 / 1（按距离三态） | opacity 1 |
| 共存允许 | ❌ 禁止 | ✅ 允许（仅此一处） |
| 为什么例外安全 | — | 预览只有 1 个摊位 → 没有"同一个数字两种形态"的**歧义**（对比的是"同一参数的两个载体"，读者是在**对齐**，不是在**比较两个摊位**） |
| 视觉降级 | — | 碑降到 40% 后**必须去饱和**（`saturate(.55)`）并去掉顶灯高光，避免 40% 的碑仍被误读为"另一组数据" |

> **例外必须显式、必须唯一、必须降级**：一旦允许"碑与三件套同屏"变成常态，§4.3 的分工就作废了。因此本例外**只在建厂预览这一个场景生效**，且必须靠 0.40 透明度 + 去饱和明确表达"这是参考，不是第二个数据源"。


### 4.4 HR 形象本身的参数化外观与行业色的关系

### 4.5 「摊主替身」的视觉定义（**Phase 2 裁定回写 · ux G2**）

> **Phase 2 裁定**：HR 的摊位就是他公司本身；**HR 本人以「摊主替身」常驻摊位，但不以真人身份实时在场**。HR 进入街区的方式是「访客模式」，并**定向**探访作品廊。
> **美术侧要的是"这家公司今天有人值班"的值班感，但绝不能有"迎接玩家"的表演**——那会让评审以为 HR 在线，是**第二个画饼**。

#### 4.5.1 五条视觉编码（把"值班"和"迎接"在像素上分开）

| # | 维度 | **值班感（采用）** | **迎接感（禁止）** |
|---|---|---|---|
| 1 | **朝向** | 站姿**正对摊位外侧 / 街道**，视线看向街道 | 转身面向玩家、头部跟随玩家 |
| 2 | **站位** | 站在摊位内一个**固定的定位圈**上（地面 0.50 m 圆环 + 一对脚印贴片，`theme.*.wire` @0.5）——"**在岗**" | 在摊位周围游走、来回踱步 |
| 3 | **呼吸** | 幅度 ±0.008 m，周期 **3.6s**（比 §3.4 作品呼吸的 3.2s 更慢——"值班"是慢的） | 幅度 ±0.02 m、周期 2.4s（那是"紧张/等待"） |
| 4 | **手部** | 双手自然下垂，idle 循环 | 抱臂、插兜、看表、抬手、指点 |
| 5 | **视线光标** | **无**——眼睛不跟随玩家 | 目光追随、点头、"看着你" |

> **判据（一句话）**：**"他在这里，所以我能问这家公司的事"，而不是"他在这儿等我"。** 前者是公司属性，后者是人的在线状态——后者我们没有。

#### 4.5.2 替身与名牌 / 工牌的分工（**三重载体，不重复**）

| 载体 | 位置 | 内容 | 视觉规则 |
|---|---|---|---|
| **摊位名牌**（门楣 / 立柱顶） | 摊位上方 1.85 m | 「**公司名 · 职位**」——**不写 HR 姓名** | 摊位 = 公司，不是个人 |
| **胸前工牌** | y = 1.28 m | 行业色底 + 职位缩写（4 字内） | 行业色**只落在这里**（§4.4.2），是替身身上唯一的彩色点 |
| **替身本人** | 摊位内 | 西装（低饱和中性，**不含行业色**）+ 站位圈 | 替身是"背景角色"，参数才是主角 |

> **为什么名牌不写 HR 姓名**：一旦写名字，玩家会自然地把它当成"一个可以对话的人"（"张伟在这儿"），而我们要的是"**这家公司在这儿**"（"某某科技在这儿"）。**名字会把公司人格化，破坏 project.md 3.3 的反羞辱基线。**

#### 4.5.3 「值班」的表达落在摊位上，不落在人身上

| 元素 | 规格 | 说明 |
|---|---|---|

## 5. 跨端交互的视觉表达

### 5.1 HR 点击求职者作品集看详情（"拾起"转场）

> **Phase 2 已解掉 R3（ux 2026-10-27）**：求职者的空间在**独立的「作品廊」场景**（见 §7），HR 通过三条路径**定向**进入某一个求职者空间：

> - **E2 主动探访**（「我的」页 → 「人才」标签 → 检索到**某一个**地址）——**检索结果是地址，不是排行榜**
> - **E3 演示直入**（演示控制台「以 HR 视角查看某求职者空间」）——仅 Demo 环境可见
>
> 因此本节的对象是**作品廊里的「我的展位」与「示例他人展位」两个**，**不依赖真实第二人**。以下四段转场与承载方式无关，可直接实现。

#### 5.1.1 四段转场

| 段 | 时长 | 缓动 | 内容 |
|---|---|---|---|
| **① 拾起** | 0–320 ms | `cubic-bezier(.22,1,.36,1)` | 作品卡脱离轨道，沿**抛物线**飞向相机：起点 = 卡当前位置，终点 = 屏幕中心偏左 38%（屏幕坐标）。飞行中卡面**持续朝向相机**（billboard），视觉尺寸从 0.62m 放大到占屏宽 46%；同时**背景玻璃的模糊半径从 28px 提到 56px**（用 CSS `backdrop-filter` 提模糊代替 GPU 后期，省一半帧时间） |
| **② 落位** | 320–560 ms | `cubic-bezier(.4,0,.2,1)` | 作品停在中心偏左；右侧滑出**玻璃详情板**：宽 380，圆角 20，padding 16，复用 GcCompanyCard 的玻璃配方 + 内高光 + 双层阴影；内容 = 作品图 + 标题 + 一行说明 + 3 个结构化字段（背景 / 角色 / star·fork 数）+ 「看线上链接」次按钮 |
| **③ 停留** | — | — | 详情板常驻；背景场景保持 56px 模糊；Esc 或点击空白关闭 |
| **④ 归位** | 0–180 ms（面板）→ 180–500 ms（作品） | `cubic-bezier(.4,0,1,1)` → `cubic-bezier(.22,1,.36,1)` | 详情板淡出 180ms；作品缩回原轨道位并恢复原尺寸与朝向 320ms；背景模糊回 28px（600ms） |

#### 5.1.2 视觉细节

- 拾起过程中作品卡**保留自身的描边与玻璃材质**（不变成平面图片）——保持"这是 3D 里的东西"的连续性。
- 详情板入场：`translateX(24px) → 0` + `opacity 0→1`，200ms（沿用 ui-system-v3 §8.8 抽屉规范）。
- 一次交互只有 **1 个操作反馈**（详情板）+ **1 个状态变化**（作品从"轨道"变为"被拾起"，轨道位留下一个 40% 透明度的空位轮廓）。禁止同时出 toast + XP 上浮 + 缩略图（ui-system-v3 §7.1 反馈收敛铁律）。

#### 5.1.3 降级

`prefers-reduced-motion: reduce` → 取消拾起飞行（作品直接缩放到目标位 120ms），详情板 120ms 淡入；背景模糊保持 28px 不变（模糊变化也算运动）。

## 7. 作品廊场景的视觉规格（**独立场景 · 求职者的地址**）

### 7.0 前置声明与复用边界

> **Phase 2 裁定（ux §1.3 / §3.4.2 / C4 / R7）**：求职者的空间**不在招聘街区里**，而在独立的「**作品廊**」场景。本节是 Phase 1 对该场景的视觉定调。

| 边界 | 规定 | 理由 |
|---|---|---|
| **不进顶栏、不改罗盘** | 顶栏三 Tab 与导航器**四臂罗盘**一律不动；作品廊从**街道路牌**与**「我的」页**进入 | 四臂罗盘是 ui-system-v3 §8.5 已通过真实浏览器验收的组件（§9.4 布局铁律第 3 条：罗盘文字会被 viewBox 裁切，改五臂必然重踩） |
| **复用 v4 的 OCC 五条契约** | 主光方位 135° / 仰角 55°、模糊↔景深、描边同源、接触阴影同向、玻璃与场景反明度 —— **全部沿用** | **"同一个世界"的唯一证据是光学一致性，不是风格相似** |
| **复用同一套主题反相** | 浅/深主题切换、玻璃反相规则与街区**完全一致** | 切换主题时两个场景必须同时换相，否则"另一个世界"会露出拼贴感 |
| **不单独配色** | 只新增 `role.gallery.fog` / `seal` 两组**同色相密度变体**（§6.1），**不引入任何新色相** | 作品廊是街区的一部分，不是第二个产品 |
| **Demo 范围** | **1 个「我的展位」+ 1 个「示例他人展位」**，其余展位位留**空龛** | ux D5 / R2：24 天内新开一个场景的成本被低估；空龛在叙事上是对的——**这是地址集合，不是展厅** |

> **本节定义的是"密度与雾"的差异，不是"新风格"。** 街区是广场，作品廊是走廊；两者共用材质、令牌、光照与主题机制。

### 7.1 空间语法：**环形走廊 + 转角隔断**（推荐与理由）

#### 7.1.1 三个候选的对比

| 候选 | 空间感 | 与街区可区分？ | 「1 视野 1 展位」是否**物理**保证 | 成本 | 判定 |
|---|---|---|---|---|---|
| **A 环形走廊 + 转角隔断** | 走廊 / 地址 / 门牌 | ✅ 街区是"十字路口 + 开阔广场 + 远景天幕"；作品廊是"折角走廊 + 近雾 + 视线尽头是墙" | ✅ **结构性保证**（折角遮挡，与玩家站位无关） | 中（新场景壳；地面/材质/光照可复用） | **✅ 采用** |
| B 展位网格（开敞平面） | 展台 / 集市 | ⚠️ 只靠围栏或地毯分区，仍是"广场"语法 | ❌ 靠自觉——抬头就能看到第二个展位 | 低 | ❌ 否决 |
| C 街道延伸的另一条巷子 | 与街区同构 | ❌ **完全同构** | ❌ 巷子是直的，走廊尽头之前就看得到第二块门牌 | 中 | ❌ **否决（最危险）** |

#### 7.1.2 推荐 A 的三条理由

1. **折角是唯一能提供"物理保证"的结构。** 展位的不可见性由**几何**决定，而不是由"我们规定你不许看"。这直接把 project.md 3.3「求职者空间之间永不并排」从**规则**升级为**物理约束**——**规则靠自觉，物理靠设计**。
2. **同族但不同构。** 同族 = 同一套玻璃体块、同一套线框网格、同一套发光数据体、同一套 OCC；不同构 = 街区开阔、亮、天幕可见；作品廊低一档、近雾、网格更细、视线尽头是墙。玩家一眼能分清"我在公司广场"还是"我在某个人的地址门口"。
3. **它天然承载"地址"这个产品概念。** 走廊 = 街道，门牌 = 门牌，门禁 = 门禁。HR 在访客模式下"检索到某个地址后进入一次"，有了物理对应物——**不是一个排行榜，是一个门牌号**。

> **C 方案为什么最危险**：它会让"作品廊"读起来像"街区的另一条街"，于是求职者的空间又变成了"街上的一家公司"——**空间上并排，语义上并排，project.md 3.3 直接失效**。而且直巷子的尽头只要有第二块门牌，"永不并排"就破产。

#### 7.1.3 关键尺寸（**由 §3.4 的作品环绕半径反推**）

| 项 | 尺寸 | 由什么反推 |
|---|---|---|
| 作品环绕主轨道半径 | **2.20 m** | §3.4.1（既有规范） |
| 展位凹龛**进深** | **3.20 m** | 环绕半径 2.20 + 作品卡半宽 0.31 + 余量 0.69 → **作品环绕不穿墙** |
| 走廊**净宽** | **2.40 m** | 玩家直径 0.60 + 侧身余量；也保证环绕作品不越界 |
| 展位凹龛**宽** | **4.60 m** | 门框柱 0.90 × 2 + 净开口 2.80 |
| 环廊**外接圆半径 R** | **16.0 m** | 十二边形边长 **8.28 m**（= 2R·sin 15°）；凹龛口到下一个折角 **5.08 m** |
| 隔断**高** | **2.60 m** | > 玩家眼高 1.60 m；且高于门框 2.10 m 的可视上沿 |
| 隔断**厚** | **0.35 m** | 玻璃墙最小合理厚度（双层玻璃 + 框） |
| 环廊段数 | **12 段**（6 展位凹龛 + 6 实墙隔断，交替） | ux「6 个展位位，每两个之间一道转角隔断」 |

### 7.3 「允许被探访」的门牌 / 门禁与敲门开门动效

#### 7.3.1 三态门禁（**形状编码优先于颜色**，WCAG 1.4.1）

| 态 | 门框 | 门牌上的**形状标记** | 颜色 | 能否进入 |
|---|---|---|---|---|
| **开放**（允许被探访） | 门洞敞开，无遮蔽 | **开口圆环**（C 形，缺口朝下 30°） | 铭牌边框 = `--role-candidate-accent` / `accentDark`（浅 7.75 / 深 4.53） | ✅ 敲门可开 |
| **私密**（不允许被探访） | 门洞被**封门玻璃**遮住（半透，**看得见里面有光，但进不去**） | **闭合横线 + 实心挂锁轮廓**（几何，不是文字） | 封门玻璃 = `--role-gallery.seal` / `sealDark`；铭牌边框 = 中性 `theme.*.wire` @0.5 | ❌ 敲门 → 「此展位未开放探访」 |
| **已探访**（ux X9） | 同开放态 | 开放标记**不变**；铭牌右下角多一枚 **Ø8 px 实心圆点** | 中性 `theme.*.wire` @0.6 | ✅ |

> **去掉颜色仍可辨**：开放 = **开口**，私密 = **闭合 + 锁**。这比"绿色=可以、灰色=不行"稳健得多。
> **"已探访"标记不告知是谁看的**：一个无信息的实心点，不写"张 HR 看过"——那会把作品廊变成社交广场。

#### 7.3.2 HR 敲门 → 门开启动效（**访客模式进入展位**）

| 段 | 时长 | 缓动 | 内容 |
|---|---|---|---|
| ① **叩门** | 0–140 ms | `cubic-bezier(.2,.8,.2,1)` | 门牌 `emissiveIntensity` 0 → 1.2；铭牌整体沿门框**下沉 0.02 m 后回弹**（像被敲了一下） |
| ② **开门** | 140–380 ms | `cubic-bezier(.22,1,.36,1)` | 封门玻璃（私密态则**不发生**）从中间裂开：两片沿 Y 轴分离 ±0.42 m，`scaleX 0→1` |

| 规则 | 说明 |
|---|---|
| **私密态的敲门** | ②③④ **全部不发生**；只做① 的叩门反馈 + 提示条「此展位未开放探访」——**门不能开，就不要演开门** |

| **一次交互的反馈收敛** | 一次敲门 = **1 个状态变化**（门开）+ **1 个反馈**（门牌亮起）。不叠加 toast、不叠加 XP 上浮（ui-system-v3 §7.1） |

### 7.4 孪生网格 / 地面 / 雾 / 光照基调（**低一档亮度**）

| 项 | 招聘街区（基线） | **作品廊** | 差异的理由 |
|---|---|---|---|
| **地面孪生网格** | 1.0 m 一格，`theme.*.wire` @0.28，线宽 1px | **0.5 m 一格**，`theme.*.wire` @0.18，线宽 1px | 更细更密 = **个人尺度**（街区的 1 m 格是城市尺度）；更淡 = 不与内容抢注意力 |
| **地面材质** | 玻璃地坪 `opacity .62`，`roughness .18` | 同材质，**opacity .52**，**roughness .30** | 少反光 = 更哑 = 更私密 |
| **雾** | 日 `near 40 / far 190`；夜 `near 34 / far 160` | **日 `near 22 / far 110`；夜 `near 18 / far 95`** | 18–20 m 外就基本被吞掉 → 走廊尽头是"白墙"不是"天空" |
| **雾色** | `theme.*.fog` | **`role.gallery.fog` / `fogDark`**（`theme.*.fog` 的同色相深一档） | 不引入新色相（"不单独配色"的落地） |
| **天幕** | `theme.*.skyTop → skyHorizon` 直连 | 同两色，但 **horizon 被雾吞 62%** | 同上 |
| **主光（key）** | 方位 **135°** / 仰角 **55°**，强度 1.0 | **同方位同仰角**，强度 **×0.85** | **OCC-1 不变——这是"同一世界"的唯一证据** |
| **环境光（hemi）** | 1.0 | **×0.78** | 低一档亮度 |
| **曝光** | 1.0 | **×0.88** | — |
| **角色色自发光** | `emissiveIntensity` 1.2（日）/ 1.9（夜） | **×0.9** → 1.08 / 1.71 | 强调色仍可在暗底上读出，但不抢主体 |

> **一句话**：街区是**广场**（开阔、亮、远景多、天幕可见）；作品廊是**走廊**（低一档、近雾、网格更细、视线尽头是墙）。
> **差别在密度与雾，不在风格**——材质、令牌、光照机制、主题反相全部共用。

#### 7.5.1 街道路牌（唯一入口）

#### 7.5.2 发现性（**分级唤醒，同一时刻最多两个在亮**，沿用 §5.2.1）

| 提示 | 触发 | 表现 |

#### 7.5.3 转场四段（总 **1.2 s**）

| 段 | 时长 | 缓动 | 内容 |
|---|---|---|---|
| ① **相机下压** | 0–120 ms | `cubic-bezier(.2,.8,.2,1)` | 俯角 +8°，画面轻微下移，露出牌面 |
| ② **玻璃吞屏** | 120–440 ms | `cubic-bezier(.22,1,.36,1)` | 路牌面板**放大到全屏**——**用玻璃本身做转场载体** |

### 7.6 「永远 1 视野 1 展位」的视觉实现（**转角 / 隔断 / 雾墙 选一**）

| 方案 | 机制 | 能否物理保证 | 成本 | 判定 |
|---|---|---|---|---|
| **转角（折角走廊）** | 视线沿直廊段延伸，被下一个折角挡住 | ✅ **几何保证，与玩家站位无关** | 中 | **✅ 采用（主机制）** |
| 隔断（独立玻璃墙） | 展位之间插一面玻璃隔断 | ⚠️ 部分保证（受高度与角度限制） | 低 | ✅ **采用（加强层）** |
| 雾墙（浓雾） | 用雾把第二个展位吞掉 | ❌ **不保证**（走近雾就散） | 最低 | ⚠️ **仅作冗余保险** |

#### 7.6.1 采用：**转角为主 + 隔断加强 + 雾冗余**（三层保险）

| 层 | 作用 | 规格 |
|---|---|---|
| **L1 几何（主）** | 十二边形**折角**环廊 | 外接圆半径 **R = 16.0 m**，正十二边形边长 **8.28 m**；12 边交替为 6 个展位凹龛 + 6 段实墙；走廊净宽 **2.40 m**；凹龛进深 **3.20 m**、宽 **4.60 m**（门框柱 0.90 × 2）；隔断高 **2.60 m**（> 眼高 1.60 m） |
| **L2 隔断（加强）** | 转角处加厚 + 内凸 | 转角隔断厚 **0.35 m**，并沿半径方向**内凸 1.20 m** 伸进走廊，形成"折角口袋"——即使玩家贴到走廊中线，也看不到转角后的展位 |
| **L3 雾（冗余）** | 保险 | `near 22 / far 110`（§7.4）→ 18 m 外的第二展位被雾吞到不可辨 |

> **为什么雾不能当主机制**：雾是**距离的函数**，玩家一走近雾就散了——**它挡不住好奇的人，只挡得住远处的人**。"永不并排"是**产品承诺**，不能建立在"他大概走不过去"上。**几何才是承诺，雾只是冗余。**
> **为什么隔断不能单独当主机制**：隔断挡得住平视，挡不住**仰视**——玩家可以越过 2.60 m 的隔断看到后方展位的光谱环与要价云。折角走廊则从**空间拓扑**上就没有"上方"这条通路。

#### 7.6.2 机检（**Phase 3 必做项**）
