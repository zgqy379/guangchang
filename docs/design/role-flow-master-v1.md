## 0. 一页读懂（给决策者）

### 0.1 这次要解决什么

现有 Demo 是一个**单向下行**的产品：HR 的参数被空间化，求职者在街区里看。它缺三件事——
**① 谁在用（双角色）② 用户自己能不能被空间化 ③ 两类人怎么在不互相伤害的前提下相遇**。

本次方案给出的三个核心答案：

| 问题 | 答案 |
|---|---|
| 两类人在同一个 3D 空间里怎么共处？ | **不在同一个空间里**。求职者的空间独立为「作品廊」场景，与招聘街区物理隔离。 |
| 求职者在街区里会被围观/排名吗？ | **不会**。「永不并排」从一条君子规则升级为**物理约束**（任一帧可见求职者展位 ≤ 1）。 |
| 「上传照片生成 3D 形象」在纯静态 Demo 里做不到怎么办？ | **不假装能做到**。三档通道抽象（replay / local / live）+ 诚实降级文案，把"等 10 分钟"如实讲出来。 |

### 0.2 最重要的一句判断

> **我们不能自己画一个"正在生成"的饼。**
> 这个项目的产品内核是"反画饼"。如果我们的 Demo 里出现假进度条、假"AI 已还原"、隐瞒 652 秒的真实等待，
> 那产品自己就变成了它要批判的东西。**诚实降级不是功能缺失，是这个产品最强的论据。**

### 0.3 三个必须承认的事实约束

1. **无后端**：浏览器端不可能调用 Aholo API（Key 绝不能进前端，这是当前的安全底线）。
   → 所有"现场生成"必须有诚实降级路径。
2. **24 天、单人**：Phase 2 原排期 23 天零缓冲且未计视觉落地/重构/盲审/录屏/部署。
   → 工程侧修正为 **21 天 + 3 天缓冲**（8 期 P0–P7）。
3. **资产预算是硬约束**：HR 形象 16MB、办公空间 17MB、玩家 Avatar 3MB。
   → 首屏必须**零 3D 资产**、零 WebGL 上下文、零 `.glb` 请求。

## 1. 角色体系总览

### 1.1 两类人

| | **求职者（C 端 · 永久免费）** | **HR（B 端 · 付费）** |
|---|---|---|
| 第一任务 | 30 秒内判断"这家值不值得去" | 5 分钟内让我的参数被看见、且不被质疑 |
| 核心成功指标 | 每会话 ≥1 次**有效投递** | 建厂完成率 ≥60%；发布后 7 日被访问率 ≥40% |
| 失败定义 | 逛了 10 家一家没投 = 失败（读不懂，不是逛得不够） | 建厂中途退出未发布 = 失败（参数→空间这条链路没让人信） |
| 最大风险 | **被比较 / 被处刑** | **画饼被拆穿** |

### 1.2 三条不对称原则（本方案的地基）

| # | 不对称 | 落地 | 依据 |
|---|---|---|---|
| **A** | **对象不对称** | 求职者的对照物是**公司参数**（山/月/楼）；HR 的对照物是**作品**。**人不对人** | project.md 3.3 |
| **B** | **空间不对称** | 公司在**招聘街区**（四街 64 摊）；求职者在**作品廊**（独立场景）。两者从不并排出现在同一视野 | project.md 3.3 |
| **C** | **时间不对称** | 公司是**常设摊位**（发布即固定陈列）；求职者空间是**有门牌的地址**（HR 主动敲门才进得去） | project.md 5.1 / 5.4 |

## 2. 首屏角色选择

### 2.1 核心决策：首屏**零 3D 资产**

> ✅ **已实现（2026-10-27，commit `ded1a26` + `a104ef4`）**
> 落地文件：`web/src/components/role/RoleGate.tsx` + `role-gate.css` · `App.tsx`（首屏不挂 `<Canvas>`）
> **实测：首屏 3D 资产请求 3 个 GLB → 0 个；传输量 8.49MB → 0.31MB（红线 5MB）；canvas 数 1 → 0；控制台零错误；三断点零溢出零重叠。**

| 项 | 决策 | 理由 |
|---|---|---|
| 首屏 3D | **不做**。纯 DOM/CSS/SVG 双龛 | ① 首屏最大风险是"打开即崩"不是"不够炫" ② three.js+R3F 进 bundle ≈600KB gzip ③ 多一个 WebGL 上下文（iOS Safari 内存上限）④ 选完角色 2 秒后就进真 3D 街区，第一印象本就建立了 |
| 原 Tier C 降级 | **不存在**（SVG 是矢量，无限缩放） | 原设计的三档降级被这条论证直接消灭 |
| 验收 | DevTools 按 type 过滤：首屏 **0 个** `.glb`/`.spz`/`.ktx2`/`.ply`；`getContext('webgl2')` 必须为 null | 可判定、可自动化 |

> **实施中发现的真根因（比规格里写的更关键）**：删 `useGLTF.preload` 只解决一半 —— `App.tsx` 的 `mode` 初始值是 `'single'`，`<Scene>` 在首屏就渲染 → `CompanyPlot` → `AssetProp` → **渲染期** `useGLTF` 照样拉 2.23MB。
> **真正让首屏归零的是"首屏不挂任何 `<Canvas>`"**，这正是本节的设计。教训见 lessons §10.8。

### 2.2 两张角色卡：五重编码（任意去掉两重仍可辨识，满足 WCAG 1.4.1）

| # | 维度 | 求职者侧 | HR 侧 |
|---|---|---|---|
| 1 | **形状** | 环形（轨道 + 节点） | 立柱（碑形 + 光条） |
| 2 | **预览内容** | 环绕自身的数据粒子 + 环形作品玻璃卡 | 悬浮钞票山缩影 + 参数碑缩影 |
| 3 | **冷暖光** | 冷光（青白粒子 + 冷补光） | 暖光（逛厂币橙钱山 + 暖金补光） |
| 4 | **色相** | `--role-candidate-accent`（冷青 `#16C0B6`） | `--role-hr-accent`（逛厂币橙 `#d98e32`） |
| 5 | **文字** | 「我是求职者」/「逛厂看公司，不看广告」 | 「我是 HR」/「让参数被看见，不被质疑」 |

> **角色色为何不复用行业四色**：若求职者用互联网蓝、HR 用智造橙，会暗示"求职者=互联网行业/HR=智造行业"，与四行业街区直接矛盾。
> 角色色为新增语义色，**永不承载白字**（同行业色规则），只用于描边/图标/粒子/≥24px 图形。

### 2.3 角色色必须走 light/dark 双模

浅色主题下冷青 `#16C0B6` 配白玻璃会糊。需各配深色变体（Phase 1 §6 令牌增量 v1.1 已补）。

### 2.4 对比度复核：**浅色主题存在真实缺陷**，需垫实底（深色主题无问题）

> **主理人独立验算（2026-10-27，两轮）**：
> 第一轮结论"现有配对全部达标"**不完整**——第二轮按"玻璃是半透明的，**背景是变量**"重算后才找出真实问题。
> **教训：半透明浮层的对比度不能用单一背景算，必须按最坏背景验算。**

#### 2.4.1 实际生效的令牌（读 `web/src/styles.css:30-66`）

| 主题 | 玻璃 | 墨色令牌 | primary | secondary | muted |
|---|---|---|---|---|---|
| **夜间**（白玻璃 `.72` + 深墨） | `rgba(255,255,255,.72)` | `#0b0e1a` / `#39414d` / `#454c59` | — | — | — |
| **白天**（深玻璃 `.72` + 浅字） | `rgba(11,14,26,.72)` | `#e6edf3` / `#b7c2cc` / `#b0bcc8` | — | — | — |

#### 2.4.2 按最坏背景验算（玻璃压在场景色上）

**夜间主题**（白玻璃压暗场景，全部达标）：

| 背景 | 合成底 | primary | secondary | muted |

| skyHorizon `#1c2440` | `#BFC2CA` | 10.77 ✅ | 5.77 ✅ | 4.84 ✅ |
| ground `#141a26` | `#BDBFC2` | 10.43 ✅ | 5.59 ✅ | 4.69 ✅ |

**白天主题**（深玻璃压亮场景，**3/6 背景不达标**）：

| 背景 | 合成底 | primary | secondary | muted | 判定 |
|---|---|---|---|---|---|
| **skyHorizon 最亮** `#f4f8fb` | `#4C5059` | 6.87 ✅ | **4.48 ❌** | **4.20 ❌** | **FAIL** |

> **根因**：`--ui-glass-fill` 的 `.72` 透明度不足以在**最亮背景**上保证文字可读。玻璃越透明、场景越亮，越吃亏。
> **注意 v4 §2.3.3 与本节的差异**：§2.3.3 只对「角色卡」这个特定场景做垫底修正，而**其余玻璃浮层（名片卡 / HUD / 导航器 / 对比篮坞 / 抽屉 / toast）压在亮天幕上时同样不达标**。

#### 2.4.3 修正方案：全站垫实底（双层结构）

```text
底：--ui-glass-underlay   浅色 rgba(11,14,26,.86) → 合成 ≈#2B2F3A
                        深色 rgba(255,255,255,.86) → 合成 ≈#DEE0E4
面：--ui-glass-fill 渐变（保留 blur 28px / saturate 180% / 内高光 / 双层阴影）
```

修正后（**最坏背景下仍达标**）：

| 主题 | primary | secondary | muted |
|---|---|---|---|
| 白天（深底 `#2B2F3A`） | 11.32 ✅ | **7.39** ✅ | **6.92** ✅ |
| 夜间（浅底 `#DEE0E4`） | 14.55 ✅ | **7.80** ✅ | **6.54** ✅ |

- **影响面**：名片卡 / HUD / 导航器 / 对比篮坞 / 演示控制台 / 抽屉 / toast / 角色卡 —— **全部垫实底**。
- **工程约束**：`--ui-glass-fill` 语义不动，新增 `--ui-glass-underlay`（避免存量代码回归）；`background-color` 必须写在 `background` 之后才能压住渐变。
- **连带规则**：玻璃卡片内**禁用 muted 色**（图例/次要标签改用 secondary）。
- **验收**：按**最坏背景**（浅色主题压 skyHorizon / 夜间主题压 skyTop）取色复核，不是随便找个位置看。

> **元教训（已写入 lessons §10.1）**：**半透明浮层的对比度必须按最坏背景验算**；设计文档里的历史值与"算一次就够"的做法都会漏掉真实缺陷。

### 2.5 首屏 = 角色选择 + 一条直达街区的默认焦点出口

> ✅ **已实现（commit `ded1a26`）**：默认焦点实测落在 `.gc-role-gate__direct`（「直接逛招聘街区 →」）。
> ⚠️ **实施中发现的坑**：`focus()` 会滚动页面 —— 移动端首屏内容 1275px > 视口 844px，自动聚焦把标题推出视口（rect.top = -439）。
> 修法：`focus({ preventScroll: true })` + 触屏（<768px）不自动聚焦。见 lessons §10.9。

> **这是对"角色选择削弱第一印象"这一风险的正式处置。**

**风险**：评审在 15 秒内要判断"这是个 3D 产品"。一个纯 SVG 的选角色页，在录屏视频的第一帧无法自证 3D。
（补充事实：当前 Demo 的首屏并非街区，而是 `App.tsx:96` 的 `'single'` 模式——"逛一家"单公司展台 + 左侧参数面板。所以首屏的 3D 含量本就低于预期，风险小于直觉，但结论仍成立。）

**处置**：角色选择**不再是"3D 之前的一道门"，而是"3D 里的一个岔路口"**。

```
打开 → 双龛角色选择（求职者冷色 / HR 暖色，纯 SVG）
  ├─ Tab 序第一位 / 默认焦点 / Enter 直达 → 「直接逛招聘街区」→ 街区鸟瞰
  ├─ 「我是求职者」→ 形象定制 → 街区
  └─ 「我是 HR」→ 建厂向导 → 街区（访客视角）
```

- 「直接逛招聘街区」是**默认焦点按钮**，视觉权重不低于两张角色卡 → **评审按 Enter 即进街区**。
- 录屏第一帧是选角色、第二帧就是街区鸟瞰。
- 回访用户记住上次角色 → 直接落在对应分支。
- 这条同时满足"首屏提供角色选择"的产品要求与"3D 第一印象"的评审要求，**两者不冲突**。

## 3. 求职者流程

### 3.1 形象获取四路径

| 路径 | 做法 | 等待 | 性质 |
|---|---|---|---|
| **A · 照片贴入** | 本地 Canvas 裁切 512² + 直方图调色 → alphaTest 面片贴在预设 3D 形象头部 | **≤1 秒** | **主路径** |
| **B · 预设形象池** | 直接选预生成形象 | 0 | 兜底 |
| **C · 演示回放** | 走 replay 通道，模拟 Lux3D 真实链路 | 85s 先验 | 演示叙事 |
| **D · 稍后再定制** | 先进街区，随时回来改 | 0 | 降低门槛 |

**路径 A 升为主路径的理由**（Phase 1 提出、主理人追认）：
① 唯一 **100% 纯前端、零失败率、零 API 依赖**的路径；
② **照片不出浏览器**（本地 Canvas 处理），直接命中 project.md 7.6「自拍即时转换后不留存原始照片」；
③ 兑现了用户需求里最核心的感受——"我这张照片真的出现在 3D 里"。

**路径 A 的两条补规格**：
- **人像分割降级链**：自动分割（可选）→ 失败则椭圆/圆角蒙版 + 边缘羽化。**绝不出现"整张矩形照片贴在头上"**。需定羽化 px 与圆角比。
- **直方图调色映射**：亮度/对比度从照片统计量映射到面片材质参数，并做**肤色偏移保护**（避免整体偏色把脸染绿）。

### 3.2 生成通道 Channel 抽象（本次方案最优雅的一处架构）

```
Channel = { id, label, stages[], estimate, poll(), abort() }

replay —— 演示回放，26s 加速播放真实阶段叙事
local —— 本地脚本离线生成后回填（tools/gen_*.py）
live  —— 未来接后端代理
```

> **等待态的视觉、阶段叙事、进度算法、失败处理、退出机制 100% 复用，只有数据源不同。**
> 将来接上后端，UI 一行不改。

**replay 三条诚实规则（不可协商）**：
1. 「演示回放」chip **常驻不可隐藏**；
2. 剩余时间显示**真实剩余**（如"真实生成还需 00:41"）；
3. 结果页标注为回放产物。

### 3.3 个人参数 → 形象具象化

**铁律（project.md 7.7）**：滑杆实时驱动 = 不能现场等 Aholo 生成。**因此任何需要重生成的参数，一律不做成滑杆。**

| 参数 | 控件 | 3D 反馈 | 延迟 | 类型 |
|---|---|---|---|---|
| 发型 | 分段选择器（6 段） | 头顶 mesh swap | 即时 | A |
| 服装 | 分段选择器（4 段） | 躯干 mesh swap | 即时 | A |
| 主色 | 滑杆 0–100 | HSV 插值 | 即时 | A |
| 配饰 | 芯片组（5 个） | 挂点 mesh 显隐 | 即时 | A |
| 体型比例 | 滑杆 −1→+1 | scaleX/scaleZ | 即时 | A |
| 肤色 | 滑杆 6 档 | 头部材质替换 | 即时 | A |
| **气质风格** | **按钮组（3 个，不是滑杆）** | **需重生成整模 ≈90s** | 异步 | **B** |
| 期望薪资 | 滑杆 6–100 万（词典 `expected_salary`） | 头顶要价云逐层长高 | 即时 | A |
| 学历/证书 | 拖拽排序（词典 `credential_order`） | 入口铭牌重排 | 即时 | A |

**主理人裁定 C1（重要）**：**外观参数不进词典**。
理由：词典的护城河价值在于"招聘参数→空间语言"的**跨公司可比较性**，外观装配不具跨主体可比性，混入会稀释词典语义纯度。
但要加一条实施约束：外观参数走**独立的"形象装配表"**（不叫词典），且**每个外观参数仍须满足「参数三要件」**——3D 载体 + 即时反馈 + 可见性分级。这样"每个参数都有载体"的红线不破。

> **术语澄清（Phase 2 纠正了主理人的用词撞车）**：
> **三件套** = HR 侧悬浮参数载体（钱袋/切口牌/日月）；
> **参数三要件** = 任何参数的落地三条件（3D 载体 + 即时反馈 + 可见性分级）。
> 两者同表并列，撞车从"靠记性"变成"查表可解"。

### 3.4 作品集悬浮于形象周围

**排布**：轨道中心 = 求职者脚下；主轨道半径 **2.20m**；作品中心高度带 **1.05–1.75m**（与人眼齐平偏上）；起始角偏置 **22.5°**。

| 数量 | 形态 |
|---|---|
| ≤8 件 | 单层，角度均分 |
| 9–16 件 | 双层：下层 8 片 r=2.20m；上层 8 片 r=2.00m，角偏置 +22.5° |
| >16 件 | 合并为「作品塔」2–4 座，每塔 3–6 片竖叠 |

**形状即编码**（即使全部去色，剪影仍可区分）：

| 作品类型 | 载体 | 几何 |
|---|---|---|
| 平面作品（UI/插画/摄影） | **玻璃卡**（矩形） | 0.62×0.44×0.02m，opacity .78，图像作 emissiveMap |
| 项目卡片（仓库/链接） | **全息板**（方形） | 0.50×0.50×0.01m，底部 star 计数灯条 |
| 3D 作品 | **实体展台**（圆形） | 玻璃圆台 Ø0.60×0.28 + 作品缩模 |

**运动模型**：**作品静止、人动**（自转会让作品跑过玩家眼前无法阅读）。常态仅呼吸浮动 ±0.012m / 3.2s。玩家进入 1.2m → 径向推出 0.35m 并转向正对（320ms）。

**降级**：移动端 / `deviceMemory ≤ 4` → 只渲染最近 6 件 + 1 座作品塔。

### 3.5 隐私三档（硬验收：私密件**不渲染**）

作品级三档（公开 / 仅 HR 可见 / 私密）+ 全局开关。
**验收必须是截图核验"它不渲染"**，不能只验证"能显示"。

### 3.6 求职者在街区里的任务流

逛 → 读参 → 参观 → 投递 → 对比 → 收集。

**"我的档案"在 3D 中的呈现**（作品廊六件套）：
脚下能力地砖路 `glowPath` · 路旁作品森林 `glowForest` · 头顶要价云 `salaryCloud` · 身后技术栈光谱环 `spectrumRing` · 环绕作品集 · 入口铭牌 `nameplate`。

|---|---|---|---|

| 读法 | 远看标识：碑高=总包 / 5 灯条=五险 / 顶灯=下班 | 近看仪表：钱袋层数 / 切口大小 / 日月形态 | 不同 |

**同屏互斥三态（硬验收）**：>14m 只碑 / 10–14m 交叉淡化 / <10m 只三件套。

### 4.4 HR 在街区中的存在形态（Phase 2 的明确答案）

> **HR 的摊位就是他的公司本身；HR 本人以「摊主替身」常驻摊位，但不以真人身份实时在场。HR 进入街区的方式是「访客模式」——以访客标记浏览，并定向探访「作品廊」。**

- 摊位名牌写**公司名 + 职位**，不写 HR 姓名。
- 求职者的空间**不在街区里**，而在作品廊；HR **不能浏览作品廊、不能排行、不能围观**，只能在收到投递后或定向检索到某个地址后**进入一次**。
- HR 的浏览权是**定向的**，不是全景的。
- 街头的 NPC 是"人气"，不是"可被投递的候选人"。

**摊主替身美术**（G2）：若 24 天内挤不进，退化为复用 `PlaceholderHR` + 换配色，**交互规则全部保留，仅观感降级**。

### 4.5 HR 点击求职者作品集看详情（用户明确点名的交互）

**触发路径（三条）**：
1. 收到投递 → 工作台 → 打开该求职者空间地址
2. 「我的」页检索到某一个地址 → 进入
3. 作品廊「示例他人展位」（演示用）

**转场（两套场景，勿混用）**：

| 场景 | 转场 | 触发 |
|---|---|---|
| **走近聚焦**（Phase 1 §3.4.3） | 作品径向推出 320ms → 相机对准 420ms → 详情扇板 `scale .94→1` + `opacity 0→1` 280ms | 玩家靠近作品 1.2m 内 |
| **点击拾起**（Phase 1 §5.1） | 作品抬起 → 拉近 → 详情板从右滑入 | HR/用户**点击**某件作品 |

**详情板内容**：作品大图 + 标题 + 类型标签 + 简介 + 创作时间 + 链接（外链）。
**权限校验**：私密作品点开 = **无任何残影**（连占位都不给），不是灰显。

**四条统一规则**：
1. 每个 `<Canvas>` 归属唯一场景，切换 = 卸载整棵 3D 树。
2. **禁止模块级 `useGLTF.preload`**（现存违规 3 处：`AvatarActor.tsx:183`、`AssetProp.tsx:45`、`HRStand.tsx:39-40`）。
3. 禁止在 `main.tsx`/`App.tsx` 顶层 import 任何 3D 组件。
4. **新增环境变量一律用非路径形态令牌**（MSYS 会把路径形态 env 改写成 `C:/Program Files/Git/...`，T8 根因）。

## 9. 项目是否需要重构？——明确结论

> **需要，但必须是"加法式重构"，不是"翻盖式重构"。**

### 9.1 一句话结论

**现有 Demo 的四份提交物（可运行链接 / 视频 / 报告 / 源码）已经达标**——本次核对确认：Pages 与魔搭双端已上线并经真实浏览器验收（控制台零报错）、视频 39.9s 实机录屏、报告书 v2 已编译 3 页、源码已转公开。
**因此双角色体系是纯加分项，不影响提交底线。**

### 9.2 但有三条硬伤必须先修（不是"重构"，是"还债"）

| # | 硬伤 | 为什么必须先修 |
|---|---|---|
| 1 | **首屏实测 5.62MB，超 5MB 红线 12.4%** | 根因是三处模块级 `useGLTF.preload`（`AvatarActor.tsx:183` 3.08MB + `AssetProp.tsx:45` 2.23MB + `HRStand.tsx:39-40` 16MB）。**删两行即降到 ≈0.35MB** —— 全计划性价比最高的一项，且零风险 |
| 2 | **draw call 2136 vs 红线 ≤200** | 移动端帧率是项目生死线（project.md 7.5）。这会让"有趣 25%"的评审在真机上直接判负。修 M6a（5h，低风险）即可吃到 60% 收益 |
| 3 | **无 ErrorBoundary** | `OfficeViewer` 一抛错整树白屏 —— 这是 T8 事故的同构风险，而 T8 已经真实发生过一次 |

> 附带发现：`public/assets/money/gold-coins.glb`（1.45MB）在 `src/` 中零引用，是死资产，不进首屏请求但白占 dist 体积。

### 9.3 执行序：**三轨并行**（不是纯串行）

> **Phase 2 提出并经主理人核实的判断**：盲审从 6.7 提到 7 分是**已知收益**，双角色是**未知收益**——而现在双端都还没过门禁。因此默认执行序应为「美术收尾优先冲 7 分 → 再做双角色」。
> 但主理人保留一条修正：双角色里有三项**同时提升现有 Demo**，把它们单列为并行的"还债轨道"，做它们不会挤压美术收尾。

```
轨道 A（保底，每周必做）  → 美术收尾：电影感灯光 / 摊位个体识别 / 导航器 → 冲盲审 7 分
轨道 B（还债，顺手提质）    → P6a preload 修复 + M5 ErrorBoundary + R8 dispose
                             + M3 progress.ts + M6a 占位人形 InstancedMesh
轨道 C（加分，做多少算多少）→ P0 首屏 → P1 词典双端化 → P2 形象面板 → P3 作品廊 → P4 建厂
```

> **去重说明（Phase 3 已确认）**：轨道 B 的「M2 词典双端化」与 Tier A 的「P1 词典双端化」是**同一件工程**（都指向 `HRPanel.tsx:13-19` 的 `FIELD_BY_ID` 硬编码 + `ParamForm` 通用化），**合并计入 P1，不重复计算**。故轨道 B 不含 M2。

**轨道 B 为什么值得与轨道 A 并行**（每一条都同时改善现有 Demo）：

| 项 | 人时 | 同时改善了什么 |
|---|---|---|
| **P6a 首屏 preload 修复** | 6 | 首屏 **5.62MB → ≈0.35MB**，直接回到 5MB 红线内。删两行代码，零风险 |
| **M5 ErrorBoundary** | 1 | 修的是 T8 同构事故风险（`OfficeViewer` 一抛错整树白屏） |
| **M3 progress.ts** | 2 | 对比篮刷新不丢（当前 `App.tsx:165` 是局部 state） |

**轨道 C 的定位**：双角色方案的**提交后第一个迭代**，不是提交前的最后一搏。
**其中 P1 词典双端化（12 人时）价值特殊**——它修的是"词典即引擎"名不副实，这是项目的**立意本身**，不是新增功能。

#### 9.3.1 三轨之间的依赖与冲突（实施时必须知道）

| 关系 | 说明 |
|---|---|
| **轨道 B ↔ 轨道 A：无冲突** | B 改的是体积/健壮性/持久化，A 改的是光照/识别度/导航器。**唯一交叠点是 M6a（占位人形 InstancedMesh）同时服务两者** —— 它既减 draw call，也让摊位个体识别度更好 |
| **轨道 A 内部有依赖** | **摊位个体识别（B）依赖光照层次（A）先落地** —— 先调光，再在光的语境里做识别，否则识别方案可能在改光时被推翻 |

| **同一文件不可并发改** | `styles.css`、`App.tsx`、`StreetScene.tsx` 会被多轨触及 → **必须串行**，或每次改动单独成 commit 保证可回滚 |
